# ROBOT COMMAND CONTRACT

## 1. Architectural Principles

This contract establishes the canonical command envelope for future communication between the RoboFest 6.0 platform and future hardware layers (e.g., ESP32). 

### Command Request vs. State Mutation
- **Command (Intent):** "Turn on torch", "Move arm to X/Y", "Move robot forward"
- **State (Truth):** "Torch is currently ON", "Arm is at X/Y", "Robot is at position X/Y/Z"

The architecture enforces a strict one-way flow of authority for physical safety:

**Command Request (UI/Mission/Simulation)**
    ↓
**Safety Engine & Permission Evaluation** (`safety.movementPermission`, `safety.torchPermission`)
    ↓
**Authoritative Robot State Mutation** (`robotState.ts`)
    ↓
**Digital Twin & Future ESP32 Hardware Adapter**

The future ESP32 adapter must **NEVER** bypass this flow. It must receive its finalized, safety-approved commands directly from the authoritative mutations, rather than intercepting raw UI input.

## 2. Command Contract Reference

### 2.1 Locomotion (Tracks)
- **Command Name:** `UPDATE_LOCOMOTION`
- **Purpose:** Commits a physical delta movement (X, Y) to the crawler tracks over a time delta.
- **Parameters:**
  - `x` (number): Expected new longitudinal position in meters.
  - `y` (number): Expected new vertical position in meters.
  - `trackOffsetDelta` (number): Value mapping track wheel rotation (meters).
- **Valid Range:** `x` between `-2.0` and `18.0`. `y` between `-29.0` and `29.0` (as per `robotConfig`).
- **Source of Truth:** `useRobotStore.getState().position`
- **Safety Permission:** `movementPermission`
- **Authoritative Mutation:** `updateLocomotion(x, y, trackOffsetDelta)`
- **Acknowledgement Model:** Hardware must report actual encoder-derived `x`/`y` telemetry back to `platformStore`. The hardware adapter must reject/fail execution if the physical tracks are stalled or slipping.
- **Simulation-capable:** YES.
- **ESP32 Intended:** YES.

> **CRITICAL HARDWARE DEPENDENCY (Locomotion Intent):** 
> The UI/Keyboard triggers a state called `locomotionIntent` (a directional vector). This is **operator intent**, NOT an approved hardware command. Future hardware adapters MUST NOT directly pipe `locomotionIntent` to physical motors. They must only consume the approved position updates generated by `updateLocomotion` (which interlocks with `movementPermission`).

### 2.2 Arm Position
- **Command Name:** `SET_ARM_POSITION`
- **Purpose:** Moves the linear actuator (X) and transverse axis (Y) of the cutting arm.
- **Parameters:**
  - `xExtension` (number): Extension in meters.
  - `yPosition` (number): Cross-axis position in meters.
- **Valid Range:** `xExtension` `0.2` to `1.0`. `yPosition` `-0.3` to `0.3`.
- **Source of Truth:** `useRobotStore.getState().arm`
- **Safety Permission:** `movementPermission`
- **Authoritative Mutation:** `setArmPosition(y, x)`
- **Acknowledgement Model:** Hardware accepts, executes, and reports actual position via telemetry, or rejects if limit switch/stepper fault occurs.
- **Simulation-capable:** YES.
- **ESP32 Intended:** YES.

### 2.3 Torch (Ignition)
- **Command Name:** `SET_TORCH`
- **Purpose:** Activates or deactivates the plasma/oxy-fuel cutting torch.
- **Parameters:**
  - `enabled` (boolean): `true` to ignite, `false` to extinguish.
- **Valid Range:** `true` / `false`
- **Source of Truth:** `useRobotStore.getState().torch.enabled`
- **Safety Permission:** `torchPermission`
- **Authoritative Mutation:** `setTorch(enabled)`
- **Acknowledgement Model:** Hardware reports actual torch status (`IGNITED`, `OFF`, `FAULT`) via Gas telemetry. The command is rejected by hardware if gas pressure is inadequate or ignition fails.
- **Simulation-capable:** YES.
- **ESP32 Intended:** YES.

### 2.4 Electromagnet
- **Command Name:** `SET_ELECTROMAGNET`
- **Purpose:** Energizes or de-energizes the central electromagnet.
- **Parameters:**
  - `enabled` (boolean): `true` to energize, `false` to de-energize.
- **Valid Range:** `true` / `false`
- **Source of Truth:** `useRobotStore.getState().electromagnet.enabled`
- **Safety Permission:** NOT YET DEFINED (No current safety rule restricts electromagnet mutation).
- **Authoritative Mutation:** `setElectromagnet(enabled)`
- **Acknowledgement Model:** Hardware reports actual electromagnet current via hardware telemetry. Hardware rejects if coil temperature is critical or circuit is open.
- **Simulation-capable:** YES.
- **ESP32 Intended:** YES.

### 2.5 Emergency Stop
- **Command Name:** `TRIGGER_EMERGENCY_STOP`
- **Purpose:** Immediately drops the safety permission levels to EVACUATION/CRITICAL, mechanically interlocking movement and torch ignition.
- **Parameters:** None.
- **Valid Range:** N/A
- **Source of Truth:** `usePlatformStore.getState().safety.emergencyStateActive`
- **Safety Permission:** None (This command *creates* the restriction).
- **Authoritative Mutation:** `safetyEngine.ts` evaluating `forceEStop`. (Currently injected via `telemetrySimulator.setScenario`).
- **Acknowledgement Model:** Hardware immediately opens safety relays, cutting power to torch and drive motors, and reports physical E-STOP button state back to telemetry.
- **Simulation-capable:** YES.
- **ESP32 Intended:** YES.

### 2.6 Cutting Path Planner
- **Command Name:** `SUBMIT_CUT_PLAN`

## 3. Acknowledgement Envelope Model

To support future network integrations without implementing WebSockets now, all commands must conceptually support a future response envelope tracking the following states:

1. **ACCEPTED:** Command safely evaluated by the platform and queued to hardware.
2. **REJECTED_SAFETY:** Command immediately dropped by the platform's `safetyEngine` (e.g., trying to move arm during an E-Stop).
3. **REJECTED_INVALID:** Command violates mechanical boundaries (e.g., moving arm to `x=5.0`).
4. **EXECUTED:** Hardware adapter confirms the physical actuator achieved the target state.
5. **FAILED:** Hardware attempted execution but failed (e.g., motor stall, ignition failure).
6. **EMERGENCY_STOPPED:** Command was interrupted mid-execution due to an E-Stop event.

*Note: This architecture assumes no physical network transport layer exists yet.*
